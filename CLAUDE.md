# Correspondence Register

A per-package correspondence register for Indian national-highway EPC contractors. It ingests every letter between the contractor, the Authority Engineer and the Project Director, extracts reference numbers, dates, chainages and contract clauses, links letters into threads by citation, and reconstructs the dated chronology of a dispute on demand.

It is **not** a chatbot over documents. It is a claim-ready evidentiary register with retrieval on top. The output is used to argue extension-of-time claims in front of arbitral tribunals.

This is a pre-sales demo build running on 10 documents: one contractor, one package, one deep thread — a single dispute chronology carried end to end.

## Architecture at a glance

```
frontend/   Vite + React + TypeScript. Plain CSS Grid, no component library, no table library.
backend/    Python 3.11 + FastAPI. Pydantic models are the HTTP contract and the LLM output schema.
db/         PostgreSQL 18 schema. SHA-256 is the document identity. Triggers enforce immutability.
fixtures/   Frozen OCR + LLM output. Replayed by FixtureOcr / FixtureLlm in demo mode.
storage/    Local blob store (S3-shaped interface). SHA-256 content-addressed.
```

- **PostgreSQL is the single source of truth.** No Neo4j, no Redis/Celery, no separate vector database. pgvector is present but demoted — semantic retrieval is never authoritative evidence.
- **OCR supplies geometry. The LLM supplies meaning.** They are joined by exact code-point alignment. If the LLM's verbatim substring is not findable in the OCR text, the field is `unresolved` and the letter is flagged `needs_review`. No bounding box is stored for an unresolvable value.
- **The LLM extracts. The database computes.** Elapsed days is `DATED` arithmetic in Postgres. No number a tribunal will see is ever generated by a language model when a deterministic computation can produce it.
- **Ingestion is offline, reproducible, and pre-computed.** `PIPELINE_MODE=fixture|live`. The demo replays only S2 and S3; S0, S1, S4–S8 run for real. A demo that runs OCR/LLM live over meeting-room wifi is a demo that fails in front of the one prospect who matters.

## How to run it

```bash
# Database
createdb correspondence_register
psql -d correspondence_register -f db/schema.sql
psql -d correspondence_register -c "CREATE EXTENSION IF NOT EXISTS pg_trgm;"

# Backend
cd backend && python3.11 -m venv .venv && source .venv/bin/activate
pip install -e .
cp .env.example .env   # fill in DATABASE_URL
python -m scripts.seed_upload_package    # prints a package_id; paste it into frontend/src/lib/api.ts UPLOAD_PACKAGE_ID
uvicorn app.main:app --port 8000 --reload

# Frontend (separate terminal)
cd frontend && npm install && npm run dev    # http://localhost:5173
```

## The design system, in one paragraph

A despatch register is a bound instrument. Ruled columns, a running serial that nothing reorders, and a status gutter that annotates without altering. Cool grey-blue ground (`#E8EBEE`), deliberately colder and darker than scanned paper so a scan always reads as a distinct physical object laid on a desk. Four colours with meaning — `flag-review` (red), `flag-verified` (green), `locate` (blue), absence — and a fifth is a bug. Noto Sans + Noto Sans Mono for everything, Archivo caps for column heads. Mono is a semantic rule, not a costume: **if a value could be transcribed into a claim, it is set in mono.** No cards, no shadows, no elevation, no chips/badges/pills, no rounded corners above 2px, no KPI tiles, no charts, no progressive disclosure.

**All frontend work goes through Impeccable.** `DESIGN.md` overrides Impeccable's defaults. Do not introduce a second design skill — Taste Skill, shadcn presets, anything in that slot will conflict. Run `/impeccable audit` before showing any screen.

## Voice

Factual and terse. Labels, not sentences. Never celebratory, never explanatory-friendly.

- "94 days" — not "Wow, 94 days!" and not "It took 94 days for a response"
- "3 documents need review" — not "Oops! We had trouble with a few files"
- No empty states with illustrations. An empty register says "No documents match these filters."
- No onboarding tone. Assume the reader knows what a chainage is.

## Constraints that govern every decision

- **Light mode only.** Shown in meeting rooms and projected. No theme toggle, no dark mode, do not build the token indirection for one.
- **Desktop only, 1366×768 minimum.** No responsive breakpoints below 1280px. No mobile.
- **Bilingual content: English and Devanagari** in the same line. Devanagari matras exceed the Latin em box — `line-height: 1.55` minimum, no `overflow: hidden` on single-line boxes that may contain Devanagari, no `text-transform: uppercase` in any region that can contain it. Never transliterate, never restyle. Test every text component with a mixed line.
- **Dates are `DD MMM YYYY` — `14 Jun 2024`.** Never numeric-only (`14/06/2024` reads as 6 April to non-Indian arbitration counsel). Never ISO. Never relative.
- **`DATED` and `RECEIVED` are separate columns.** Never merge them. Never backfill one from the other. Where only one is known, the other cell is empty with an em dash in `--ink-3`.
- **Elapsed days always carries both endpoints.** Never a bare number. Never coloured, never a bar, never benchmarked.
- **Counts always carry their denominator.** `10 of 10`, never `10`.
- **Immutability is enforced by the database, not by convention.** `documents`, `extracted_fields`, and `letters` reject direct mutation via trigger. The only sanctioned paths are `record_field_verification()` and `record_field_correction()`. Don't bypass them with raw `UPDATE`s.

## Things that will get the work rejected

These are disqualifying, drawn from what the author confirmed would make a polished result feel wrong.

**Startup / SaaS aesthetics**
- Cards, `border-radius` above 2px, any shadow, chips/pills/badges/tags, accent-coloured filled buttons, icon-only controls, gradient text, glass, blur, coloured halos, emoji.

**Analytics-dashboard aesthetics**
- KPI tiles, hero metrics, charts, sparklines, progress rings, donuts, gauges, heatmaps, trend arrows, scores, grades, indexes, "health" metrics. The tool reports; it does not appraise.

**Progressive disclosure**
- No drawers, no modals over data (modals are only for destructive confirmation), no accordions, no "show more", no collapsed rows, no tooltips that carry data found nowhere else. Any click required to reach data already retrieved is a defect.

**Ambiguity**
- No unlabelled count. No elapsed-days figure without its endpoints. No date in a format readable two ways. No unit-less number. No inferred or backfilled value at the same weight as an extracted one.

**Nostalgia**
- No cream/parchment, no sepia, no rubber-stamp texture, no faux-bound edges, no typewriter face, no serif set to signal officialdom.

**Evidentiary defects**
- No `latency_days` column. Compute it. The LLM extracts; the database computes.
- No confidence score surfaced to users. `validation` is the signal; it is `exact` / `normalized_exact` / `unresolved`.
- No unique constraint on `(package_id, letter_ref_normalized)`. Real OCR produces genuine duplicates; route them to `needs_review`, never reject the row. The database records the fact; it never decides which one is right.
- No `CHECK (received >= dated)`. A misapplied stamp or retrospective receipt is evidence, not a bug. Flag it.
- No soft-delete on letters. Voided letters keep their serial, permanently: `17, 18, 20` with `19` permanently voided is correct; silently collapsing `20` back to `19` is not.

## Pipeline quick reference

Nine stages (`PIPELINE.md`). `job_type` in `ingestion_jobs` does not mirror them 1:1 — `map` folds into `validate` (no queue hop for a cheap deterministic step), `publish` is the transaction boundary at the end of `link` (a commit, not a retriable job), and `embed` has no S-stage because it is off the critical evidentiary path.

| Stage | Job | What happens |
|---|---|---|
| S0 Intake | `intake` | SHA-256 → document identity, duplicate detection, original written once |
| S1 Rasterize | `rasterize` | 300 DPI, deskew/despeckle/threshold *as a policy to benchmark*, not a default |
| S2 OCR | `ocr` | Provider → page text + word tokens with normalized 0..1 bboxes |
| S3 Extract | `extract` | Claude Opus 5, strict schema, every field carries `verbatim` |
| S4 Validate | `validate` | Deterministic. `verbatim` must be code-point-findable in OCR text or the field is `unresolved`. Folded with S5. |
| S5 Map | `validate` | char offsets → tokens → bounding rects (per-token, not just union) |
| S6 Assemble | `link` | Letters split out, duplicate refs flagged, serials assigned deterministically |
| S7 Link | `link` | Citations resolved, threads materialized with versioned `thread_memberships` |
| S8 Publish | `link` | `is_current` flipped in one transaction. Register entry appears. |

**S6–S8 are one transaction. That transaction contains no OCR call, no LLM call, and no object-storage upload.** Ever. A half-extracted letter never appears in the register.

**Prompt caching is the cost lever.** Contract conditions, clause list, party roster are byte-identical across every letter in a package. Render order: `tools` → `system` → `messages`. Volatile content after the last breakpoint. A `datetime.now()` anywhere in the prefix silently kills the benefit — verify `usage.cache_read_input_tokens` is non-zero across consecutive calls.

## Coding conventions

**Frontend**
- Plain React + CSS Grid, no component library, no table library. Filtering runs server-side in Postgres — the loaded page can never be the universe.
- `position: sticky` for the frozen register columns (STATUS, SR, DATED, LETTER REF).
- TanStack Query for server state.
- Types generated from the backend's OpenAPI schema. One source of truth for the shape of a letter.
- Self-host Noto Sans, Noto Sans Mono, Archivo. Subset with care — Noto Sans Devanagari is large; preload the two faces above the fold.

**Backend**
- Pydantic models do three jobs from one definition: validate the LLM's structured output, define the HTTP contract, generate the OpenAPI schema.
- Job queue is a Postgres-backed table with `SELECT ... FOR UPDATE SKIP LOCKED`, not Celery. The job history is the audit trail.
- Storage interface (`BlobStore`) is the same shape in dev (local filesystem) and prod (S3 with Object Lock). Migration is a directory copy; `immutable=True` becomes an Object Lock retention header instead of a no-op.

**Database**
- `chainage_m` is `int4range` in metres. `Km 12+400` → `12400`. GiST index for the overlap filter.
- `daterange` where a letter covers a period, plain `date` otherwise. `DATED` and `RECEIVED` as separate columns.
- `pg_trgm` for fuzzy reference-number matching — OCR confuses `2O24` and `2024` constantly.
- Recursive CTEs for thread traversal.
- Composite foreign keys to keep cross-package contamination out: a field cannot claim a letter from a different run, a citation cannot link letters across packages, a letter's thread and parties are scoped to the letter's own package.

## Re-extracting an already-published document

When a new pipeline run produces a candidate letter, S6 must decide whether it is a new version of an existing logical letter or a brand new one.

1. **Primary match:** exact `letter_ref_normalized` within the package, scoped to `is_current` letters. A match means "same logical letter" — the candidate inherits that letter's `serial`.
2. **Fallback:** page-range overlap on the same `document_sha256`. Covers a case where the new OCR fixed a previously-garbled reference.
3. **No confident match:** insert as a new logical letter with a fresh serial, mark it `needs_review` with a note that it arrived from a reprocessing run. A human confirms. The database records the ambiguity; it never resolves it silently.

Supersede is three statements in order, because a naive two-step version hits two real bugs that only surface by running it against live Postgres:

```sql
INSERT INTO letters (..., is_current) VALUES (..., false);  -- not yet current: satisfies the FK and the partial unique index
UPDATE letters SET is_current = false, superseded_by = :new_id WHERE id = :old_id;  -- vacate the slot
UPDATE letters SET is_current = true WHERE id = :new_id;                            -- take it
```

The old letter's `extracted_fields`, `citations`, and `review_events` all remain exactly as they were — fully queryable as history. The `register` view (which filters `WHERE l.is_current`) and other live-facing queries stop showing the old version.

## What "deterministic" actually means for serials

Serial is **immutable once assigned, forever, regardless of what arrives later.** That is the load-bearing guarantee. Sorting the view never changes it; the `SR` column always shows the immutable register serial.

Batch-reproducibility is a *narrower, secondary* property that holds for a full rebuild over a fixed, complete document set. It does **not** hold for incremental, real-world ingestion: a letter dated 12 Mar that arrives on a Tuesday *after* letters dated 13 Apr were already serialed on Monday gets Tuesday's next serial, not a slot implied by its date. An earlier version of this doc conflated the two — do not reintroduce that conflation.

A gap can still appear, deliberately: a letter later found to be a duplicate is **voided** (`letters.voided_at`, `void_reason`), never deleted and never renumbered.

## What is not in scope for the demo

- pgvector / semantic search — the deterministic filters carry the demo
- Neo4j — probably permanently
- Auth, RBAC, multi-tenancy, user-action audit log
- S3 Object Lock / WORM
- Job retries, resumability, partial-failure handling
- Annexure bundle generation (job 7) — describe, don't build, unless it is a sales talking point
- Incremental re-ingestion heuristic beyond the S6 reprocessing-match logic that already ships
- Database-role-level immutability (`REVOKE UPDATE, DELETE` from the app role) — a production-hardening item, not a schema one. No roles exist yet to revoke anything from.

## When in doubt

- The author is the contracts manager's advocate, not the engineer's. When this codebase and a "better" idea collide, the codebase usually wins. The audience will use this in front of a tribunal.
- The product's differentiator is job 5: click any extracted value, land on the original page with it highlighted. Every decision in OCR, LLM output contract, and validation should be checked against that one requirement.
- "The database records the fact; it never decides which one is right" is the most repeated pattern in this codebase. Look for it before reaching for application logic to resolve ambiguity.
