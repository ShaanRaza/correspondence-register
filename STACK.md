# STACK.md

Tech stack proposal. Model IDs and pricing **verified against official Anthropic documentation on 2026-08-30**.

## The decision that drives everything else

The product's differentiator is **job 5** — click any extracted value, land on the original page with it highlighted. That one requirement determines the OCR choice, the LLM output contract, and the quality gate that makes `Needs review` mean something.

**OCR supplies geometry. The LLM supplies meaning. They are joined by exact string alignment.**

1. Rasterize the page at 300 DPI, deskew, despeckle, adaptive-threshold.
2. OCR → word-level tokens, each with `{text, page, bbox, char_start, char_end}` plus a reading-order text serialization.
3. Send that OCR **text** (and the page image alongside it) to Claude under a strict output schema requiring every extracted field to carry the **exact verbatim substring** as it appears in the OCR text.
4. Map substring → char offsets → word tokens → union of their boxes = the highlight rectangle.
5. **If the returned substring is not byte-present in the OCR text, reject the extraction** and flag the row `Needs review`.

Step 5 is the whole quality story. An extraction that cannot be located on the page does not get to be a fact. It is a cheap deterministic check, it is what gives `--flag-review` a defensible meaning, and it is the difference between an evidentiary register and a chatbot with citations it made up.

Corollary, and a rule for the whole system:

> **The LLM extracts. The database computes.**

Elapsed days is arithmetic on two dates in Postgres. No number a tribunal will see is ever generated by a language model when a deterministic computation can produce it.

## Frontend — React + TypeScript + Vite ✓

Agreed. Additions:

- **No component library.** Not shadcn, not MUI, not Radix themes, not Mantine. Every one of them ships cards, chips, shadows, drawers and radii that [DESIGN.md](DESIGN.md) explicitly bans; you would spend more effort overriding than building. Radix **primitives** (unstyled) are acceptable for the two or three controls where accessibility is fiddly (combobox, date field).
- **No table library.** Not TanStack Table. The column set is fixed and known (11 columns), and filtering must run **server-side in Postgres** so it applies across the whole package rather than the loaded page. Client-side table libraries assume client-side data. Plain React + CSS Grid, with `position: sticky` for the frozen columns.
- **TanStack Query** for server state. Reasonable, unopinionated visually.
- **Fonts self-hosted**, per DESIGN.md: Noto Sans, Noto Sans Mono, Archivo. Subset with care — Noto Sans Devanagari is large; subset to Devanagari + Latin + the punctuation actually used, and `preload` the two faces above the fold.
- Types generated from the backend's OpenAPI schema. One source of truth for the shape of a letter.

## Backend — Python + FastAPI

The gap in your template. Python, decisively.

**Why.** The entire ingestion pipeline is document work: PDF rasterization, image preprocessing, OCR client SDKs, layout handling, token-geometry alignment. That ecosystem is Python's and nothing else is close. Writing it in Node means reimplementing mature glue.

**Why FastAPI specifically.** Pydantic models do three jobs from one definition: validate the LLM's structured output, define the HTTP contract, and generate the OpenAPI schema that produces the frontend's TypeScript types. In a product where a field's shape is a correctness concern, having one schema instead of three is worth a lot.

**Considered and rejected:** Node/TypeScript end-to-end for single-language simplicity. The document-processing gap decides it.

**Job queue:** a Postgres-backed jobs table with `SELECT ... FOR UPDATE SKIP LOCKED`, not Celery + Redis. Ingestion is a multi-stage resumable pipeline (rasterize → OCR → extract → align → link), and the job history *is* an audit trail — which this product needs to keep anyway. One less datastore, and the durability story is the same one the rest of the data already has.

## Database — PostgreSQL ✓

Agreed, and it should carry more than you may be planning.

- Everything here is relational and must be transactional. An extraction run that half-commits is a correctness bug in a tool whose claim is that nothing is missing.
- **Chainage as `int4range` in metres.** `Km 12+400` → `12400`. A GiST index on the range makes job 2's chainage filter an overlap query — exact, indexed, no application logic.
- **Dates as `daterange` where a letter covers a period**, plain `date` otherwise, with `DATED` and `RECEIVED` as separate columns per DESIGN.md.
- `JSONB` for the raw OCR payload, kept verbatim next to the normalized tokens.
- `pg_trgm` for fuzzy reference-number matching — reference numbers in scanned letters are exactly where OCR errs, and `NHAI/PKG3/2O24/117` must still find `NHAI/PKG3/2024/117`.
- Recursive CTEs for thread traversal (see Graph below).

## Vector search — pgvector ✓, but demoted

Keep it, and be clear about its rank.

Primary retrieval in this product is **deterministic**: reference number, date range, chainage range, clause, party, thread. Semantic search is a secondary convenience ("letters about utility shifting") and it is never the thing an EOT claim rests on.

> **A semantically-retrieved result must never be presented as if it were deterministic.** "These six letters cite Cl. 10.3.2" and "these six letters resemble your query" are categorically different claims. If the UI shows vector results, it labels them as such, in a distinct region, and they never enter an annexure bundle without a human selecting them.

pgvector rather than a dedicated vector database because at this scale (tens of thousands of letters, not billions) it costs nothing extra: same database, same transaction, same backup, same restore drill.

**Open risk:** the embedding model must handle Devanagari. Most defaults are English-first and will quietly underperform on mixed-script content without failing loudly. Benchmark this on real letters before committing — it is the one place in this stack where a bad choice hides.

## Graph — Neo4j: my recommendation is **no**, and here is why

You asked me to explain why. The honest answer is that I do not think this product needs it, and I would rather say so now than after it is in the deployment.

### What the graph actually is here

Letters are nodes; "cites reference X" is an edge. Its real properties:

| Property | Value |
|---|---|
| Fan-out per letter | 1–3 citations |
| Cycles | effectively none — a letter can only cite earlier letters |
| Depth | a long EPC thread is 15–40 letters |
| Scale | 10 in the demo; 20k–200k letters across all packages in production |
| Queries needed | "the connected component containing letter X" and "that component in date order" |

That is a forest of shallow chains, not a densely connected graph. At 200k letters and 3 edges each, the entire edge set is ~600k rows — it fits in memory several times over. A recursive CTE over an indexed edge table answers both queries in single-digit milliseconds.

### The genuine case *for* Neo4j

It is not a silly choice, and it becomes right if the product grows in a specific direction: variable-length path queries with rich predicates, multi-hop pattern matching across heterogeneous node types (letter → clause → claim → drawing revision → dispute), or actual graph algorithms — centrality to surface the pivotal letter in a dispute, community detection to find threads that citation alone missed because someone forgot to write a `Ref:` line. Cypher is genuinely better than recursive CTEs for all of that, and that last example is a real product idea.

### Why it still loses today

1. **Two datastores means two consistency models.** In a tool whose entire proposition is *nothing is missed*, a letter present in Postgres but absent from Neo4j is precisely the failure the product claims to prevent. You would need dual-write, reconciliation, and a way to *prove* the two agree. That is permanent cost against a benefit you cannot currently name a query for.
2. **Thread membership has to be materialized anyway.** A thread cannot silently recompute differently between two viewings of the same claim — that is indefensible in front of a tribunal. So `thread_id` gets persisted on each letter by an explicit, versioned job. Once it is a materialized column, traversal happens once at ingestion rather than per query, which removes the performance argument entirely.
3. **Ops burden is not free**, least of all on a pre-sales demo.

### Recommendation

Postgres edge table + recursive CTE + materialized, versioned `thread_id`. Revisit when you can name the query you want and cannot write. My threshold — all three, not any one:

- multi-hop paths across ≥3 distinct node types, **and**
- graph *algorithms* (centrality, community detection) rather than reachability, **and**
- edge count past ~10M.

**And if you do add it:** add Neo4j as a **derived read model rebuilt from Postgres**, never as a second source of truth. The "nothing is missed" guarantee must live in exactly one place.

## Document storage — S3-compatible, content-addressed, WORM

The gap in your template, and it carries more evidentiary weight than it looks like.

- **Content-addressed.** The SHA-256 of the original bytes *is* the document id. You can then prove that the file backing an annexure is byte-identical to what was ingested — which is the actual tribunal-facing requirement, and a real sales point.
- **Originals are never mutated.** Derived artifacts (page rasters, OCR JSON, thumbnails) are separate objects keyed by `(source_hash, pipeline_version)`. When the extractor improves you re-derive without touching originals, and you can always say which pipeline version produced any given extraction. That is provenance for the *extraction*, not just the document.
- **Production:** S3 with Versioning + Object Lock in compliance mode on the originals bucket. That is the write-once story, and it is worth demoing as a claim even before it is enabled.
- **Demo:** local filesystem behind the same storage interface, with the same SHA-256 addressing. Costs nothing now, avoids a migration later.

## OCR — Google Document AI primary, Tesseract fallback

Decided by two hard requirements: **word-level bounding boxes** (job 5 is impossible without them) and **Devanagari alongside Latin, sometimes on the same line**.

| Option | Verdict |
|---|---|
| AWS Textract | **Out.** No meaningful Devanagari support. |
| Tesseract 5 + `script/Devanagari` | Free, offline, gives word boxes. Fine on clean scans, degrades badly on the photocopied-faxed-rescanned letters this domain is full of. **Keep as fallback** — and as the only option for the on-prem deals some contractors will insist on. |
| Google Document AI / Vision `DOCUMENT_TEXT_DETECTION` | **Primary.** Strongest mixed Devanagari + Latin, word-level vertices, handles skew and low DPI well. |
| Azure Document Intelligence | Comparable; better table/layout extraction, returns polygons. Reasonable alternative if the prospect is an Azure shop. |

Put all of them behind **one interface** returning a normalized `{text, tokens: [{text, page, bbox, char_start, char_end}]}`. The interface matters more than the initial pick — you will swap providers, and an on-prem deal will force Tesseract whether you planned for it or not.

**Do not use Claude vision as the sole OCR.** It reads these pages well, but it does not return reliable pixel geometry, and job 5 needs geometry. Its right role is a *second reader*: run it independently and flag disagreements with the OCR text for review. That is a quality signal, not a geometry source.

**Preprocessing earns its keep.** On this document population, deskew + despeckle + adaptive threshold at 300 DPI is often worth more accuracy than changing OCR vendors.

## LLM — Claude Opus 5 (`claude-opus-5`)

| Model | ID | Context | Max output | Input /MTok | Output /MTok | Batch in/out | Cache read | Role here |
|---|---|---|---|---|---|---|---|---|
| Claude Opus 5 | `claude-opus-5` | 1M | 128K | $5.00 | $25.00 | $2.50 / $12.50 | $0.50 | **extraction** |
| Claude Sonnet 5 | `claude-sonnet-5` | 1M | 128K | $2.00 | $10.00 | $1.00 / $5.00 | $0.20 | bulk re-runs if cost bites |
| Claude Haiku 4.5 | `claude-haiku-4-5` | 200K | 64K | $1.00 | $5.00 | $0.50 / $2.50 | $0.10 | document-type triage pre-pass |

Verified against the official models overview and pricing pages on 2026-08-30. Cache writes are 1.25x base input (5-minute TTL) or 2x (1-hour); cache reads are 0.1x. The full 1M context is charged at standard rates — no long-context surcharge.

Two notes from that check:

- **Sonnet 5's $2/$10 is now the standard price.** It was announced as introductory pricing through 31 Aug 2026; the scheduled increase to $3/$15 has been cancelled.
- **Opus 5 and Sonnet 5 use the tokenizer introduced with Opus 4.7, which produces roughly 30% more tokens for the same text** than Sonnet 4.6 and earlier. Re-baseline any token estimate carried over from an older model with `count_tokens` rather than assuming.

**Why Opus and not Sonnet.** The failure mode is a wrong clause number or a wrong date in a document that goes before a tribunal. Cost of error is high; volume is low.

**Corrected cost estimate.** My earlier figure of ~$7.50 per package was wrong — it counted only input tokens. Output dominates, because *thinking tokens bill at the output rate*. Re-estimating a 500-letter package on Opus 5, with caching and the Batch API:

| Line | Tokens | Rate | Cost |
|---|---|---|---|
| Uncached input (~2k/letter) | 1.0M | $2.50 batch | $2.50 |
| Cache reads (~20k prefix/letter) | 10.0M | $0.25 batch | $2.50 |
| Output + thinking (~3k/letter) | 1.5M | $12.50 batch | $18.75 |
| **Total** | | | **~$24** |

Roughly **$48** without the Batch API. Treat these as an order of magnitude, not a quote — measure with `count_tokens` and a 20-letter pilot before budgeting. The conclusion is unchanged and if anything stronger: the model is not the cost centre, being wrong is. But the cost lever is **output**, so `effort` is worth tuning (try `medium` for extraction) alongside prompt caching.

Implementation notes, current as of the API today:

- **Structured outputs**, not prose parsing: `output_config: {format: {...}}` with `strict: true` on the schema, so `additionalProperties: false` and `required` are enforced and the response validates exactly. Use `client.messages.parse()`.
- **Adaptive thinking**: `thinking: {type: "adaptive"}`, `output_config: {effort: "high"}`. Do not use `budget_tokens` — it is removed on Opus 5 and returns a 400.
- **No assistant prefill** on Opus 5 (400). Control format via structured outputs.
- **Prompt caching is the biggest cost lever here.** The contract's General and Special Conditions, the clause list, the party roster and the extraction schema are byte-identical across every letter in a package. Cache that prefix; put the per-letter OCR text *after* the last breakpoint. Order is `tools` → `system` → `messages`, and any byte change in the prefix invalidates everything after it. Verify `usage.cache_read_input_tokens` is non-zero across repeated calls — a `datetime.now()` in the system prompt silently kills the whole benefit.
- **Batch API for bulk ingestion**: 50% cost, results keyed by `custom_id` and returned in arbitrary order. Ingestion is not latency-sensitive; this is free money.
- **Haiku 4.5 pre-pass**: classify what a document even is (letter / drawing / minutes of meeting / test report / measurement sheet) before spending Opus on extraction. Cheap routing, not extraction.

## Cloud — India region, and ask the prospect early

**Data residency is the live constraint, not cost.** NHAI package correspondence is commercially sensitive and sometimes contractually restricted in where it may be stored. Default to an India region (`ap-south-1` Mumbai / `asia-south1`). Raise it in the first sales conversation — some of these firms will require on-prem or VPC-isolated, which is exactly why the OCR interface and the Tesseract fallback are not optional.

**Production:** AWS `ap-south-1`. S3 Object Lock is the cleanest write-once story, RDS Postgres supports pgvector, and Indian enterprise buyers are already comfortable with it.

**Anthropic API:** first-party rather than Bedrock.

**Correction to what I said earlier.** I implied `inference_geo` could pin inference to India. It cannot — the parameter takes `"us"` or `"global"` (the default), and `"us"` carries a 1.1x price multiplier on every token category. **There is no India inference geography.** So the residency story splits in two, and you should be precise about it with prospects:

- **Documents and extracted data** stay in India — S3 `ap-south-1`, RDS in the same region. You control this completely.
- **Inference** runs on Anthropic's global infrastructure. If a prospect's constraint is genuinely "no data leaves India", the hosted LLM path does not satisfy it, and you need that conversation early rather than late.

Partner platforms (Bedrock, Google Cloud) have their own regional endpoints and independent pricing, at a 10% premium over global; that is the route if a prospect requires a contractual regional guarantee. Bedrock costs some feature availability (no fast mode, no Claude API-only features).

**Demo:** do not deploy anything. A pre-sales demo on 10 documents needs zero cloud architecture.

## Required for the demo

Ten documents, one contractor, one package, one deep thread.

| Component | Demo form |
|---|---|
| Frontend | Vite + React + TS, the register and thread screens per DESIGN.md |
| Backend | FastAPI, read-only endpoints over pre-ingested data |
| Database | Postgres in Docker, full schema, `int4range` chainage, recursive-CTE threads, materialized `thread_id` |
| Document storage | Local filesystem, SHA-256 addressed, same interface as production |
| OCR | Google Document AI — it derisks the "it read Devanagari correctly" moment |
| LLM | Opus 5 extraction, strict schema, substring alignment gate |
| Fixtures | **Ingest offline, commit the results.** |

**Ingest ahead of time and ship the output.** A demo that runs OCR and an LLM live over meeting-room wifi is a demo that fails in front of the one prospect who matters. The pipeline should be *demonstrable* on request; it should not be *load-bearing* during the meeting.

Leave two or three documents genuinely flagged `Needs review`. A register that claims 10 of 10 perfect extractions on scanned Indian highway correspondence is less credible than one that says `3 documents need review` and shows why — and it is the honest way to demo the quality gate.
